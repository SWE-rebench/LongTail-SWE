# Longtail-SWE v1.1 task fixes

Release `longtail-swe-202-v1`, revision v1.1. Only task records change: no image, base commit, install step or
reference patch of the 202 benchmark tasks changes. Saved results, annotations and paper tables
(`data/selected_results_202.jsonl`, `data/results_202.*`, `data/annotations_202.json`, `data/paper_tables_202.json`)
are historical and were **not** regraded with the changed tests.

## Benchmark (202 tasks): 5 changed records

All five were found while validating every task with the reference patch (must pass) and an empty patch (must fail)
on two independent runs. After the fixes the reference patch scores 1 and the empty patch 0 on all 202 tasks.

| Task | Changed fields | What and why |
| --- | --- | --- |
| `scottarbeit__grace-800` | `FAIL_TO_PASS` | Two NUnit test names lacked their leading word `failed` (`failed resync recovery suspends observation capture`, `failed upload remains queued and blocks status-only rescan until upload succeeds`). The runner prints the full names, so the reference patch could never pass. |
| `rrousselgit__riverpod-4747` | `install_config.test_cmd` | `flutter test` ran the files concurrently, and the expanded reporter then never printed three passing `listen_test` P2P names (the open "Riverpod P2P evidence" question). Now `flutter test --concurrency=1 test/features/mutations_test.dart`; same tests. |
| `juliadiff__differentiationinterface.jl-1036` | `install_config.test_cmd` | The command installs Enzyme 0.13.215 at test time; EnzymeCore 0.8.27 (released later) removed `EnzymeRules.has_easy_rule`, so Enzyme no longer precompiled. EnzymeCore is pinned to 0.8.26 in the same `Pkg.add`. |
| `samply__blaze-3728` | `install_config.test_cmd` | `make prep` downloads `fhir-definitions-4.0.1.zip` from `speicherwolke.uni-leipzig.de`, which no longer responds. `build.clj` skips the download if the file exists and checks its SHA-256; the official `https://hl7.org/fhir/R4/definitions.json.zip` has exactly that SHA-256 (`ecd74b1d…f534`), so the command places it first (curl, wget or Java). The repository's SHA check still guards the content. |
| `scottarbeit__grace-136` | `test_patch`, `FAIL_TO_PASS`, `PASS_TO_PASS` | **Hidden-test edit (one line).** All four FAIL_TO_PASS tests passed without any change: the test's fake object store always served the whole-file object, which the existing whole-file download used. `ManifestDownloadResolvesBlocksAndReconstructsOriginalBytes` now runs with that object absent (the `stashBoundaries` mechanism the two rejection tests already use), so the bytes must come from the ContentBlocks, as the issue requires. The other three tests pass with and without the reference patch and moved to PASS_TO_PASS (FAIL_TO_PASS 4 -> 1, PASS_TO_PASS 0 -> 3). |

Known label properties kept unchanged: in 40 tasks some FAIL_TO_PASS tests already pass without a fix (39 before
plus `samply__blaze-3728`, whose tests previously could not run), and in `ark-ecs__ark.jl-625` one PASS_TO_PASS test
fails without it; the empty patch still fails all of these tasks.
